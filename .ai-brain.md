## hauntedcore dependency — real, verified via source read, not assumed

`HorrorChatMessagesPresenceBridge.java` directly imports and calls
`com.horrortricks.hauntedcore.coordinator.EventCoordinator` and
`com.horrortricks.hauntedcore.presence.PresenceState`. Confirmed this is
genuinely **optional at runtime**, not just optional-on-paper: every call
site in `HorrorChatMessagesEvents` is guarded by a cached
`ModList.get().isLoaded("hauntedcore")` check before the bridge class is ever
touched, so the JVM never links/loads `HorrorChatMessagesPresenceBridge`
(and therefore never needs hauntedcore's classes) unless hauntedcore is
actually present. This matches `mods.toml`'s `type="optional"`,
`side="CLIENT"` declaration exactly — a deliberately correct design, not a
loophole.

**Wiring used:** a Gradle composite build, not a merged multi-project build.
`settings.gradle` has `includeBuild('../hauntedcore')`; `build.gradle`
declares `compileOnly "com.horrortricks.hauntedcore:hauntedcore:1.0.0"`.
Gradle's automatic dependency substitution matches that coordinate
(`group=com.horrortricks.hauntedcore`, `name=hauntedcore` from its
`rootProject.name`) to the sibling build's project output — confirmed
working via `:hauntedcore:compileJava FROM-CACHE` appearing in this
project's own build log. `compileOnly` (not `implementation`) was chosen
deliberately: needed to compile against, but not bundled into this mod's own
jar — verified the built jar contains zero `hauntedcore` classes. This keeps
hauntedcore and horrorchatmessages as two separate mod jars, matching how
they're two separate Modrinth projects; it does **not** by itself make both
mods load together in a dev-run instance (that's `run/mods/` deploy-script
territory per RECOVERY.md section 9, out of scope here).

Each mod's own repo/build stays independent — this doesn't merge git history
or require hauntedcore to publish to its `repo/` folder first.

## ★ Follow-up fix (found while reconstructing phantomjoin): mods.toml was silently missing the hauntedcore dependency

The standard MDK `neoforge.mods.toml` template only auto-generates
`neoforge`/`minecraft` dependency blocks. The original commit above copied
that template as-is, which meant the built jar's metadata never actually
declared the (optional) `hauntedcore` dependency the real, original
`mods.toml` had — silently dropped, not carried over. Caught this while
double-checking the equivalent gap in `phantomjoin` (there it was worse,
since that dependency is mandatory). Fixed by adding a real
`[[dependencies.horrorchatmessages]] modId="hauntedcore" type="optional"
ordering="AFTER" side="CLIENT"` block to
`src/main/templates/META-INF/neoforge.mods.toml`, matching the original
decompiled `mods.toml`'s declaration. Rebuilt and confirmed the block now
appears in the generated `neoforge.mods.toml` inside the built jar.
